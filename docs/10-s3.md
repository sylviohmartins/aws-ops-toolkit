# S3: artefatos aprovados e transferência com memória limitada

Projeto: **aws-ops-toolkit**. Pesquisa oficial consultada em **18/09/2026**.

## 1. Escopo entregue e política de dados

`S3Service` oferece head, listagem de uma página, download streaming, upload de stream com comprimento conhecido e delete protegido. O gate limita chamadas lógicas; no download, o permit fica retido até terminar o corpo, não apenas até receber os headers. Um buffer de 64 KiB, limite máximo de bytes e verificação de cancelamento evitam materializar o objeto inteiro. Falhas abortam o stream remoto.

Multipart, resume de transferências, `S3TransferManager`, verificação completa de integridade e publicação do manifesto são **arquitetura alvo**. O adapter não é uma implementação de backup/restauração pronta para produção.

Por padrão, relatórios e checkpoints permanecem no armazenamento local aprovado. Exportar pre-images, post-images, failures ou relatórios para S3 exige destino explicitamente permitido pela organização, classificação de dados, retenção, criptografia e IAM/KMS adequados. Não inferir autorização para copiar dados de produção a um bucket pessoal, a outra conta ou a outra região.

## 2. Contratos de leitura

`HeadObject` fornece tamanho/metadados úteis para planejamento, mas uma consulta seguida de Get não impede mudança concorrente do objeto. Quando necessário, fixar `versionId` ou precondição de leitura. Não transformar `AccessDenied` em “objeto inexistente”: resultado e autorização devem permanecer distintos. [HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html)

Listagem usa `ListObjectsV2`, `maxKeys` explícito de até 1000, prefixo aprovado e `ContinuationToken` opaco. Se `IsTruncated=true`, continuar com `NextContinuationToken`; não usar a última key como substituto genérico. Metadados de objetos não devem ser acumulados em lista global. O adapter entrega uma página para que a operação controle checkpoint e orçamento. [ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html)

Exemplo de uso local, após validar path e política de dados:

```java
try (var output = Files.newOutputStream(approvedTemporaryPath,
        StandardOpenOption.CREATE_NEW, StandardOpenOption.WRITE)) {
    var metadata = s3Service.download(GetObjectRequest.builder()
            .bucket(approvedBucket).key(approvedKey).versionId(approvedVersion).build(),
            output, approvedMaxBytes, cancellationToken);
    // O chamador verifica integridade e publica/renomeia o arquivo somente depois de concluir.
}
```

O adapter não fecha o `OutputStream` do chamador. A operação deve manter downloads incompletos como temporários, verificar tamanho/checksum, sincronizar o arquivo conforme sua necessidade de durabilidade e publicar o nome final de forma atômica quando suportado. Falha não pode deixar um artefato parcial parecendo relatório final válido. Não mapear uma key S3 diretamente para path local sem proteção contra traversal e colisões.

## 3. Upload de streams e idempotência

Informar comprimento exato em `RequestBody.fromInputStream`. Comprimento menor pode truncar dados; maior pode impedir a conclusão adequada. Streams de tamanho desconhecido usados por determinadas APIs síncronas podem ser integralmente bufferizados para calcular comprimento; para grandes massas, usar arquivo de staging ou multipart. O SDK exige atenção à capacidade de reabrir/resetar o stream em caso de retry. [Uploads de streams no SDK 2.x](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/best-practices-s3-uploads.html)

O exemplo `upload` aceita stream e comprimento conhecido, não implementa geração de stream repetível nem restringe sozinho o tamanho total do artefato. O chamador deve aplicar orçamento de bytes, fechar o stream e escolher política de retry. O client padrão usa uma tentativa; um upload com timeout ainda pode ter concluído remotamente e precisa de reconciliação.

Para artefatos imutáveis, planejar key determinística por operação/tipo/parte e proibir overwrite acidental com precondição. `If-None-Match: *` permite criar apenas quando a key não existe; `If-Match` protege alteração pela entidade esperada quando aplicável. Uma falha de precondição não é automaticamente retry transitório. [Escritas condicionais S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)

Exemplo de request, usando bucket e chave previamente autorizados:

```java
var request = PutObjectRequest.builder()
        .bucket(approvedBucket)
        .key(approvedArtifactKey)
        .ifNoneMatch("*")
        .contentType("text/csv; charset=utf-8")
        .metadata(Map.of("operation-id", operationId, "artifact-type", "failures"))
        .build();
try (var source = Files.newInputStream(approvedLocalArtifact)) {
    var response = s3Service.upload(request, source, Files.size(approvedLocalArtifact));
    // Registrar versionId/checksum retornados e reconciliar antes de publicar o manifesto.
}
```

Não inserir dados pessoais em key, metadata ou tags, que podem aparecer em inventários/auditoria. A política de criptografia precisa ser explicitamente compatível com o bucket: usar SSE-KMS quando exigido, com chave aprovada e permissões mínimas. O template genérico não escolhe uma chave corporativa.

## 4. Multipart e Transfer Manager

Multipart separa criação, envio de partes e conclusão. A operação alvo guarda upload ID, bucket/key, tamanho da parte, números/ETags/checksums confirmados e identidade do arquivo fonte. Só completa quando todas as partes estão confirmadas; aborta quando a operação é cancelada definitivamente, ou conserva estado explicitamente para resume autorizado. Partes incompletas têm custo de armazenamento e precisam de política de limpeza/lifecycle. O ETag de um objeto multipart não deve ser tratado como MD5 do arquivo inteiro. [Multipart overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)

O checkpoint de transferência deve vincular hash/tamanho/mtime ou identidade mais forte do arquivo de origem. Retomar com arquivo alterado pode produzir um artefato inválido mesmo que cada parte individual seja válida. `CompleteMultipartUpload` com resultado desconhecido exige verificar objeto/metadados/checksum antes de criar outro upload ou limpar partes.

`S3TransferManager` é a opção a avaliar quando uploads/downloads grandes e multipart paralelo forem frequentes. A API usa client async; escolher explicitamente a implementação baseada em CRT ou Java e seus limites, conforme suporte da versão. Pode gerenciar paralelismo e transferências de arquivo, mas não conhece as políticas de incidente, IAM, data residency ou aprovação do toolkit. [S3 Transfer Manager](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/transfer-manager.html)

Decisão inicial: client síncrono com virtual threads e streaming para operações simples; introduzir Transfer Manager somente após benchmark demonstrar ganho relevante. Limitar objetos simultâneos, partes por objeto, conexões, memória direta e bytes/s. Um gate no início da transferência não limita sozinho os requests de partes internos; esses limites precisam entrar no client async e no plano.

## 5. Delete e versionamento

Delete é uma operação de escrita explícita, com plano/dry-run por key e versão. Em bucket versionado, apagar sem version ID cria um delete marker; fornecer version ID permite remover aquela versão. Bucket com versionamento suspenso tem tratamento próprio para versão nula. Preservar identidade completa do objeto no relatório; considerar retenção/Object Lock e não tentar contorná-los. Usar `expectedBucketOwner` para fazer a AWS recusar um owner diferente do aprovado. [DeleteObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html)

O adapter chama o port de autorização para `s3:DeleteObject` e, quando há version ID, também `s3:DeleteObjectVersion`. O identificador fornecido ao port é `s3://bucket/key`; a implementação corporativa precisa resolver conta/região/owner e validar a versão/precondições no plano. Esse identificador textual **não é comprovação de propriedade do bucket**. A assinatura mínima do port não substitui um guardrail contextual completo.

Não disponibilizar exclusão recursiva de prefixo no esqueleto. Uma futura operação desse tipo deve materializar um manifesto de alvos com orçamento estrito e validar explicitamente a relação prefixo→objetos; nunca usar o primeiro resultado da listagem como autorização para apagar todo o bucket.

## 6. Manifesto, checkpoint e critérios de aceite

Publicação alvo: gerar artefatos locais → validar/redigir → transferir cada artefato com chave imutável → reconciliar checksums/versões → gravar manifesto final. Um checkpoint exportado só é retomável se também referenciar os relatórios/journals confirmados; exportar um JSON isolado não torna toda a operação recuperável.

O manifesto registra operation ID, tipos, keys/versions, tamanhos, checksums, classificação, regra de retenção, esquema e estado de completude. Falha parcial deixa manifesto incompleto, sem anunciar sucesso global. Manter listagem de uploads pendentes para retomada/limpeza autorizada.

Validar antes de homologar: objeto maior que orçamento, stream interrompido, arquivo local parcial, origem alterada entre partes, versão divergente, checksum incompatível, timeout após PUT aceito, falha de KMS, cancelamento durante transferência e quota de disco. Limites de memória devem ser medidos com arquivos superiores à heap, sem `readAllBytes()` nem buffer integral oculto.
